# เอกสารภาพรวม API — Com7 → LarkBase Sync

เอกสารนี้อธิบายหน้าที่และความรับผิดชอบของแต่ละเส้น API ในระบบซิงก์ข้อมูลการขายจาก Com7 (MySQL) ไปยัง LarkBase แบบทิศทางเดียว (one-way)

รายละเอียดคำขอ การตอบกลับ และรหัสข้อผิดพลาด ดูเพิ่มเติมที่ [api-reference.md](./api-reference.md)

Base URL (สภาพแวดล้อมท้องถิ่น): `http://localhost:3000`

---

## 1. การพิสูจน์ตัวตน

ทุกเส้นทาง **ยกเว้น** `GET /health` ต้องส่งข้อมูลรับรองของแอปพลิเคชัน Lark ในส่วนหัวของคำขอ ดังนี้

| ส่วนหัว | ความหมาย |
|---|---|
| `X-Lark-App-Id` | รหัสแอปพลิเคชัน Lark |
| `X-Lark-App-Secret` | ความลับของแอปพลิเคชัน Lark |
| `Content-Type` | `application/json` (เมื่อมีเนื้อความคำขอ) |

ระบบแลกเปลี่ยน token ของ Lark ต่อคำขอ และไม่เก็บความลับไว้ถาวร หากส่วนหัวขาดหายหรือไม่ถูกต้อง ระบบจะตอบด้วยสถานะ `401 Unauthorized`

## 2. ตารางสรุปหน้าที่ของแต่ละเส้นทาง

| วิธี + เส้นทาง | หน้าที่หลัก | ลักษณะการทำงาน |
|---|---|---|
| `GET /health` | ตรวจสอบความพร้อมของบริการและฐานข้อมูลปฏิบัติการ (ops) | ซิงโครนัส |
| `POST /base/init` | จัดเตรียมโครงสร้างตารางและฟิลด์ของ base ตามปีที่ระบุ | ซิงโครนัส |
| `POST /base/remove-partitions` | ลบตารางพาร์ทิชันของปีที่ระบุออกจาก Lark | ซิงโครนัส |
| `GET /base/status` | รายงานสถานะการจัดเตรียม (provision) ของปีที่ระบุ | ซิงโครนัส |
| `POST /sync/full` | สั่ง backfill ข้อมูลทั้งปีจากแหล่งข้อมูลไปยัง Lark | แบบอะซิงโครนัส (งานเบื้องหลัง) |
| `GET /sync/full/status` | รายงานความคืบหน้าของงาน backfill | ซิงโครนัส |
| `GET /sync/full/check` | ตรวจสอบความสอดคล้องระหว่างแหล่งข้อมูลกับ Lark | ซิงโครนัส |
| `POST /sync/full/heal` | ซ่อมแซมจุดที่ไม่สอดคล้องซึ่งตรวจพบจากการตรวจสอบ | ซิงโครนัส |
| `POST /sync/incremental` | ซิงก์แถวที่สร้างใหม่หรือมีการเปลี่ยนแปลงตาม watermark | ซิงโครนัส |
| `POST /sync/hard-full` | ล้างข้อมูลทั้งปีบน Lark และสั่ง backfill ใหม่ทั้งหมด | แบบอะซิงโครนัส (งานเบื้องหลัง) |
| `POST /sync/clear-partitions` | ล้างข้อมูลทั้งปีบน Lark โดยไม่สั่ง backfill ใหม่ | แบบอะซิงโครนัส (งานเบื้องหลัง) |

หมายเหตุ: เส้นทางแบบอะซิงโครนัสคืนรหัสสถานะ `202` พร้อมหมายเลขงาน (`jobId`) และต้องมีกระบวนการ worker ทำงานอยู่เพื่อประมวลผลคิวงาน

## 3. ลำดับการใช้งานตามวงจรชีวิต

### 3.1 การเพิ่มปีใหม่

1. สร้าง base ใน Lark และกำหนดสิทธิ์ให้แอปพลิเคชันของระบบ
2. เรียก `POST /base/init` เพื่อจัดเตรียมตารางพาร์ทิชัน
3. เรียก `POST /sync/full` เพื่อเติมข้อมูลทั้งปี
4. ติดตามความคืบหน้าด้วย `GET /sync/full/status`

### 3.2 การใช้งานประจำ

- เรียก `POST /sync/incremental` เป็นระยะ (เช่น ทุก 15 นาที หรือทุกวัน) เพื่อนำเข้าข้อมูลที่เปลี่ยนแปลง

### 3.3 การตรวจสอบและซ่อมแซม

1. เรียก `GET /sync/full/check` เพื่อตรวจหาความไม่สอดคล้อง
2. หากพบความผิดปกติ เรียก `POST /sync/full/heal` เพื่อซ่อมแซมเฉพาะส่วนที่จำเป็น

### 3.4 การกู้คืนเมื่อข้อมูลเสียหายอย่างรุนแรง

- เรียก `POST /sync/hard-full` พร้อมยืนยัน (`confirm: true`) เพื่อล้างข้อมูลปีนั้นและสร้างใหม่ทั้งหมด

### 3.5 การยุติการใช้งานข้อมูลของปี

- เรียก `POST /sync/clear-partitions` พร้อมยืนยัน (`confirm: true`) เพื่อล้างข้อมูลโดยไม่สั่ง backfill อัตโนมัติ

## 4. รายละเอียดหน้าที่ของแต่ละเส้นทาง

### 4.1 `GET /health`

**วัตถุประสงค์:** ตรวจสอบว่ากระบวนการบริการยังทำงานอยู่ และสามารถเชื่อมต่อฐานข้อมูลปฏิบัติการได้

**ขอบเขตการใช้งาน:** การเฝ้าระวังระบบ การตรวจสอบสุขภาพก่อนเรียกเส้นทางอื่น และการตอบสนองของตัวกระจายโหลด (load balancer)

**การพิสูจน์ตัวตน:** ไม่จำเป็น

---

### 4.2 `POST /base/init`

**วัตถุประสงค์:** จัดเตรียมโครงสร้างตารางพาร์ทิชัน (เช่น `itec_001` ถึง `itec_250`) และฟิลด์ตามสคีมาที่กำหนด ใน base ของปีที่ระบุ

**ขอบเขตการใช้งาน:** ดำเนินการครั้งแรกของแต่ละปีปฏิทิน หรือเมื่อเพิ่มปีใหม่เข้าสู่ระบบก่อนการเติมข้อมูล

**ลักษณะสำคัญ:** สามารถเรียกซ้ำได้อย่างปลอดภัย (idempotent) และรองรับการทำงานต่อเนื่องจากจุดที่ค้าง หากงบเวลา (budget) หมดก่อนเสร็จสิ้น

---

### 4.3 `POST /base/remove-partitions`

**วัตถุประสงค์:** ลบตารางพาร์ทิชันของปีที่ระบุออกจาก Lark (ลบทั้งตาราง ไม่ใช่เพียงข้อมูลภายในตาราง)

**ขอบเขตการใช้งาน:** การรื้อถอนโครงสร้างที่จัดเตรียมผิดพลาด หรือการเลิกใช้งานโครงสร้างของปีนั้น

**ข้อควรระวัง:** ไม่เหมาะสำหรับการล้างข้อมูลแล้วเติมใหม่โดยรักษาโครงสร้างไว้ ในกรณีนั้นให้พิจารณา `POST /sync/hard-full` หรือ `POST /sync/clear-partitions` แทน

**พารามิเตอร์เสริม:** `dryRun=true` เพื่อแสดงรายการที่จะถูกลบโดยไม่ดำเนินการลบจริง

---

### 4.4 `GET /base/status`

**วัตถุประสงค์:** รายงานสถานะการจัดเตรียมพาร์ทิชันของปีที่ระบุ โดยอ่านจากฐานข้อมูลปฏิบัติการ

**ขอบเขตการใช้งาน:** ติดตามความคืบหน้าของ `POST /base/init` และยืนยันความพร้อมก่อนเริ่ม backfill

**ลักษณะสำคัญ:** ไม่เรียก API ของ Lark โดยตรง จึงตอบสนองได้อย่างรวดเร็ว

---

### 4.5 `POST /sync/full`

**วัตถุประสงค์:** สั่งงานเติมข้อมูล (backfill) ทั้งปีจากตารางแหล่งข้อมูลใน Com7 ไปยัง Lark พร้อมบันทึกความสัมพันธ์ระหว่างแถวต้นทางกับเรคอร์ดบน Lark

**ขอบเขตการใช้งาน:** การเติมข้อมูลครั้งแรกของปี หรือการเติมปีย้อนหลังหลังจากจัดเตรียม base เสร็จสิ้น

**ลักษณะสำคัญ:** ทำงานแบบอะซิงโครนัส ต้องมี worker หากมีงานที่เกี่ยวข้องกับปีนั้นอยู่แล้ว ระบบจะคืนงานเดิมโดยไม่สร้างงานซ้ำ

---

### 4.6 `GET /sync/full/status`

**วัตถุประสงค์:** รายงานสถานะและความคืบหน้าของงาน backfill ของปีที่ระบุ

**ขอบเขตการใช้งาน:** การติดตามระหว่างดำเนินการและหลังการสั่ง `POST /sync/full` หรืองานที่สัมพันธ์กับการเติมข้อมูลทั้งปี

---

### 4.7 `GET /sync/full/check`

**วัตถุประสงค์:** ตรวจสอบความสอดคล้องระหว่างจำนวนและเนื้อหาในแหล่งข้อมูลกับข้อมูลบน Lark และแผนที่ในฐานข้อมูลปฏิบัติการ

**ขอบเขตการใช้งาน:** การตรวจสอบสุขภาพข้อมูลเป็นระยะ หรือก่อนดำเนินการซ่อมแซม

---

### 4.8 `POST /sync/full/heal`

**วัตถุประสงค์:** ซ่อมแซมจุดที่ไม่สอดคล้องซึ่งตรวจพบ โดยดำเนินการเฉพาะส่วนที่จำเป็น

**ขอบเขตการใช้งาน:** ภายหลังจาก `GET /sync/full/check` รายงานความผิดปกติ หากความเสียหายครอบคลุมทั้งปีและไม่สามารถซ่อมด้วยวิธีนี้ได้ ควรพิจารณา `POST /sync/hard-full`

---

### 4.9 `POST /sync/incremental`

**วัตถุประสงค์:** ดึงแถวที่มีเวลาอัปเดต (`UTime`) ไม่น้อยกว่า watermark ล่าสุด แล้วดำเนินการสร้าง อัปเดต หรือข้ามตามสถานะในแผนที่ข้อมูล จากนั้นเลื่อน watermark ไปยังค่าสูงสุดของรอบนั้น

**ขอบเขตการใช้งาน:** การซิงก์ต่อเนื่องหลังการ backfill รอบแรก เพื่อรักษาความทันสมัยของข้อมูลบน Lark ด้วยภาระงานที่ต่ำ

**พฤติกรรมสำคัญ**

- แถวที่อ้างอิงปีที่ยังไม่จัดเตรียม base จะถูกข้าม แต่ watermark ยังเลื่อนผ่านแถวดังกล่าว
- หากมีงานเบื้องหลังจากประเภท `full_sync`, `hard_full_sync` หรือ `clear_partitions` ที่อยู่ในสถานะพร้อมดำเนินการหรือกำลังดำเนินการ ระบบจะปฏิเสธคำขอด้วยสถานะ `409 Conflict`

---

### 4.10 `POST /sync/hard-full`

**วัตถุประสงค์:** ลบเรคอร์ดทั้งหมดของปีที่ระบุบน Lark พร้อมล้างแผนที่และสถานะที่เกี่ยวข้อง จากนั้นสั่งงาน backfill ใหม่โดยคงโครงสร้างตารางและสูตรไว้

**ขอบเขตการใช้งาน:** การกู้คืนเมื่อข้อมูลเสียหายอย่างรุนแรงจนการซ่อมแซมเฉพาะจุดไม่เพียงพอ

**ข้อควรระวัง:** เป็นการดำเนินการที่ทำลายข้อมูลเดิม ต้องระบุ `confirm: true` ในเนื้อความคำขอ ทำงานแบบอะซิงโครนัส และต้องมี worker

---

### 4.11 `POST /sync/clear-partitions`

**วัตถุประสงค์:** ลบเรคอร์ดทั้งหมดของปีที่ระบุบน Lark และล้างแผนที่ที่เกี่ยวข้อง โดยไม่สั่งการ backfill อัตโนมัติ

**ขอบเขตการใช้งาน:** การยุติการใช้งานข้อมูลของปีนั้น หรือการเตรียมพื้นที่ก่อนดำเนินการเติมข้อมูลด้วยตนเองในภายหลัง

**ข้อควรระวัง:** เป็นการดำเนินการที่ทำลายข้อมูลเดิม ต้องระบุ `confirm: true` ทำงานแบบอะซิงโครนัส และต้องมี worker

## 5. การแยกประเภทตามลักษณะการทำงาน

| ประเภท | เส้นทาง | คำอธิบาย |
|---|---|---|
| ซิงโครนัส | `/health`, `/base/*`, `/sync/full/check`, `/sync/full/heal`, `/sync/incremental`, `/sync/full/status` | รอผลการประมวลผลในคำขอเดียวกัน |
